# Hierarchy

<Lead>A **hierarchy** is nodes that sit inside each other, declared with `structure: "hierarchy"`: one table of nodes, and a `nesting` table with one row per containment. `constraints.contain` governs which rows can hold others, [layout](/layout) rules size containers and arrange their contents (`layout.contain`, `layout.dodge`, `layout.row`, `layout.column`, `layout.grid`, `layout.pack`), and `edit.hierarchy.nest` drops a node into a container or out of one. A mark's `contains` option is a shorthand for container eligibility and fitting on that mark.</Lead>

<ApiReference entries={api} />

<Section id="schema" title="Declaring the structure">

`structure: "hierarchy"` gives the dataset a `nodes` table and a `nesting` table. A `links` table is optional.

```js
schema: {
  structure: "hierarchy",
  tables: {
    nodes: {
      id: { type: "categorical", key: true, open: true },
      kind: { type: "categorical", domain: ["group", "note"] },
      x: { type: "quantitative", domain: [0, 100] },
      y: { type: "quantitative", domain: [0, 100] },
      w: { type: "quantitative", domain: [0, 600], default: 130 },
      h: { type: "quantitative", domain: [0, 400], default: 80 },
    },
    nesting: {
      child: { type: "ref" },
      parent: { type: "ref" },
    },
  },
}
```

`getData()`, `onChange` and `setData` use one array per table. A table you leave out of `data` starts empty.

<Section id="nesting" title="The nesting table">

The nesting table is declared like any other table: a field map, with a type for every column.

It needs two `ref` columns. The first names the contained node and the second names its container. Both point at the nodes table's `key: true` column, so their values are node identities. The column names are yours.

```js
nesting: {
  child: { type: "ref" },    // the contained node
  parent: { type: "ref" },   // its container
}
```

One row is one membership. A node with no row is at the top level. A node has at most one container, and cannot contain itself or any node inside it. A row from `data` or `setData` that breaks either rule is dropped with a warning, and so is a row that names a missing node.

Add any other columns you want to record about a membership. They take a `type`, a `domain` and a `default` like columns anywhere else. A row made by a drop takes each column's `default`, or the value you pass in `edit.hierarchy.nest({ defaults })`.

```js
nesting: {
  child: { type: "ref" },
  parent: { type: "ref" },
  coder: { type: "categorical", domain: ["seed", "participant"], default: "participant" },
}
```

Deleting a node removes the nesting rows that name it. Its contents move to the top level.

</Section>

<Section id="naming" title="Naming the tables">

Name the tables for your data and give each a `role`: `"nodes"`, `"nesting"` or `"links"`. A table named after its role needs no `role`, which is the short form used above.

```js
tables: {
  topics:      { role: "nodes",   fields: { … } },
  memberships: { role: "nesting", fields: { … } },
}
```

`data`, `getData()` and `setData` are then keyed `topics` and `memberships`. Marks, constraints, layouts and edits find each table by its role.

<Section id="containers" title="Containers">

Containment splits cleanly into two pieces: **eligibility** (a pure-data invariant) and **geometry** (a pixel-space layout rule).

- `constraints.contain({ parent, child, maxDepth, maxChildren })` decides which rows may hold others, which may sit inside a container, and how deep or full a container may get. It guards every edit and `setData`.
- `layout.contain({ where, padding, fit })` sets the room between a container's edge and its contents, and whether the container sizes itself to fit them (`fit: true`, `"x"`, `"y"`, or `false`).

```js
constraints: [
  constraints.contain({ parent: (d) => d.kind === "group" }),
],
layout: [
  layout.contain({ padding: 12, fit: true }),
],
```

When a chart draws different kinds of node with separate marks, or when one mark owns its own containers, the mark option `contains` is a shorthand for both:

```js
rect({
  contains: { where: (d) => d.kind === "group", padding: 12, fit: true },
  channels: {
    x: { field: "x" },
    y: { field: "y" },
    width: { field: "w", scale: null },
    height: { field: "h", scale: null },
  },
})
```

`contains: true` lets every row drawn by that mark hold others, and `contains: (d) => …` picks rows with default padding. `scale: null` reads `w` and `h` as pixels.

A fitted container writes its size back to the mark's size fields (`width`/`height`, `size`, `rx`/`ry`, or `x1`/`x2`/`y1`/`y2`), so a resize edit leaves those fitted columns alone while an empty container stays editable. When a container loses its last child, it returns to each fitted column's schema `default` and keeps its top-left corner. Declare a `default` for every fitted column; without one, the container shrinks to its padding and logs a warning.

```js
w: { type: "quantitative", domain: [0, 600], default: 130 },
```

The fitted size is in the data, so other channels can read it. The examples here place a group's name from its `h` column.

<Section id="spacing" title="Padding and spacing">

Every container keeps `padding` between its edge and its contents. The default is 10px. Give one number, or a side each; a side you leave out takes the default.

```js
layout: [
  layout.contain({ padding: { top: 30, right: 12, bottom: 12, left: 12 }, fit: true }),
  layout.dodge({ gap: 10 }),
]
```

A fitted container is sized to leave that room. A container with a size of its own moves its contents inside it.

Add `layout.dodge({ gap, where, in })` to push overlapping siblings apart. `gap` defaults to 8px, `where` picks the rows that take part, and `in` scopes it to `"all"` (default), `"roots"`, `"containers"`, or a container predicate. Round nodes keep the gap edge to edge. A `composite` dodges as a whole, with every part, its label included.

Nodes dodge their siblings: the contents of one container dodge each other, and top-level nodes dodge each other. When two overlap, the node you just dropped stays put and the other moves the shortest distance that clears it. When that leaves no room, the contents pack in reading order from the top-left. A container that grows pushes its neighbours the same way, and they take their contents along. A pushed node stays inside its container's padding, or inside the plot at the top level.

Nodes are pushed apart on release, and when data arrives through `setData`. While you drag, they are drawn where the release will put them. Seeded data is spaced once, at the start.

<Section id="arrange" title="Arranging contents">

Add an arrangement rule to `layout` to place contents in slots or packed clusters. See [Layout](/layout) for the full vocabulary, including flat tables and networks.

| Rule | Contents |
| --- | --- |
| `layout.dodge({ gap, where, in })` | Where you drop them, pushed apart when they overlap. |
| `layout.row({ gap, in })` | Left to right from the top-left. A row with a fixed width wraps at it. |
| `layout.column({ gap, in })` | Top to bottom from the top-left. A column with a fixed height wraps at it. |
| `layout.grid({ columns, gap, in })` | Equal cells, the size of the largest node, `columns` to a row. |
| `layout.pack({ gap, keep, in })` | Drawn together where you drop them, touching. |

In a hierarchy, `row`, `column`, `grid` and `pack` default to `in: "containers"`. Pass `in: "roots"` to arrange top-level nodes, or `in: (d) => …` to arrange different container kinds differently — for example `layout.row({ in: "roots" })` beside `layout.column({ in: (d) => d.kind === "lane" })`.

In a row, column or grid, the order of the contents is the answer. Drag a node within its container to reorder it. Drop one into a container and it takes the nearest slot. While you drag, the other nodes open a space where it will land. On release, every node snaps to its slot.

A pack has no order. A node you drop there moves in to touch the others, and the others stay where they are. Nothing in a pack moves until you let go, so the node you aim at holds still. Round nodes pack as circles. Boxes pack as boxes, so they meet edge to edge.

`keep` sets how a dropped node moves in:

| `keep` | The node moves |
| --- | --- |
| `"distance"` | To the free spot nearest where you let go. The default. |
| `"angle"` | Straight towards the node in the middle of the pack, or away from it, until it touches. Its direction from the middle stays the same. |

Use `"angle"` when where a node sits around the middle is the answer.

`gap` is the space between slots, 8px by default. `columns` sets a grid's cells to a row. Without it, a grid fills a fixed width, or makes a square.

```js
layout: [
  layout.contain({ padding: { top: 30, right: 10, bottom: 10, left: 10 }, fit: true }),
  layout.column({ gap: 6 }),
]
```

The order is read from the `x` and `y` columns, which hold each node's slot. A fitted container keeps its top-left corner and grows right and down. A pack is fitted round its contents.

<Section id="fixed" title="Fixed containers">

Leave `fit` off `layout.contain` and a container keeps the size it was given. Use this for regions that are part of the question: buckets, lanes, zones. Lock them with `lock` so only the cards move. Cards stay inside the bucket's padding, and a locked row stays where it is when nodes dodge. Add `layout.dodge()` to keep cards from overlapping, or `layout.column()` / `layout.grid()` to put them in slots.

The answer is the nesting table: one row per card, naming its bucket.

<Section id="gestures" title="Dragging in and out">

Put `edit.hierarchy.nest()` on the mark you drag, beside `move({ mode: "relative" })`. The move carries the node. On release, the node joins the innermost container under the pointer. Released over no container, it leaves the one it was in.

While you drag, the chart shows what a release would do. The container the node would join is outlined and grows to hold it. The container it came from keeps its size while the pointer is inside it, and shrinks once the pointer leaves. Other nodes move out of the way when `layout.dodge()` or a slot layout is active. The data changes on release. Style the outline with the `target` state of `effects`.

A container stays where it is when you drag a node past it or out of it. Released against a container's edge, the node you dropped moves clear of it when `layout.dodge()` is active.

The layout eases to its new place. Nodes make room first and a container resizes after them. The node you drag stays on the pointer. Set the time with `motion: { duration }` on the spec, in milliseconds, or `motion: false` to draw each change at once. Motion is off when the reader's system asks for reduced motion.

The same `move` moves a container, and its contents travel with it.

Rules about which nodes may go where, maximum depth, or how many children a container may hold belong in `constraints.contain(...)` (or `constraints.custom` on `table: "nesting"`). A drop a rule refuses shows no outline and leaves the data unchanged.

<Section id="external" title="Reading and setting from outside">

Containment is stored as rows, so your code reads and writes it like any other data. `getData()` returns the nesting rows and each container's fitted size.

`setData` takes the same shape. Change the nesting rows and every container re-fits. A node sent with no `x` and `y` is placed inside the container it joins, clear of the nodes already there. In an arranged container it takes the last slot.

```js
const data = chart.getData();
chart.setData({ ...data, nesting: [...data.nesting, { child: "n4", parent: "g2" }] });
```
